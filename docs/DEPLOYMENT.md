# Deploy the API for free with Render and Turso

This setup hosts only the Express API on Render Free and keeps persistent data in Turso Free. The React frontend is not built or served. No paid disk, Railway subscription, or Render Postgres database is required. Stay on the free plans and leave paid upgrades/overages disabled; free-tier quotas and service availability still apply.

## 1. Create the Turso database

Create a free Turso account and a **libSQL database**, which is the engine supported by this project's `@libsql/client` driver. With the Turso CLI:

```bash
turso auth login
turso db create agroconnect
turso db show agroconnect --url
turso db tokens create agroconnect
```

Do not add the `--tursodb` flag: this project uses libSQL, not the newer Turso engine. Copy the database URL and database authentication token into Render's secret settings. Never commit the token or place it in a `VITE_` variable. Existing local SQLite data is not uploaded automatically; a new database starts empty. If preserving existing data, export/import it through Turso's migration tools before pointing the API at it.

## 2. Create the Render service

1. Push this repository to GitHub.
2. In Render, choose **New > Blueprint**, connect the repository, and use the root `render.yaml` file.
3. Confirm the single web service uses the **Free** instance. No paid resources are declared.
4. Supply `TURSO_DATABASE_URL` and `TURSO_AUTH_TOKEN` when prompted. Render generates a private `JWT_SECRET`; keep it stable across redeployments.
5. Deploy. Render builds the API-only Dockerfile and checks `/api/health`. Schema creation and the seller-status migration run against Turso at startup before the API begins listening.

If creating a Web Service manually instead of using the Blueprint, select Docker, the repository root, the Free plan, and `/api/health` as the health-check path. Set all environment variables below yourself.

| Variable | Value |
| --- | --- |
| `NODE_ENV` | `production` |
| `TURSO_DATABASE_URL` | Your remote `libsql://...turso.io` URL |
| `TURSO_AUTH_TOKEN` | Your database authentication token |
| `JWT_SECRET` | A private random secret (generated by the Blueprint) |
| `SEED_DEMO_DATA` | `false`, or `true` if you intentionally want the README demonstration accounts and listings |
| `CORS_ORIGINS` | Optional comma-separated exact browser origins, such as `http://localhost:5173` |

Render supplies `PORT`; no manual port setting is needed. Production refuses to start without a remote database URL and token, preventing accidental use of disposable local storage. `DATABASE_PATH` applies only to local development. Environment files are not loaded automatically.

Postman, curl, and server-to-server consumers do not need CORS configuration. Browser clients require their exact origin in `CORS_ORIGINS`. JWT authentication is required independently of CORS.

## 3. Verify deployment

Use the Render-generated HTTPS domain:

```bash
curl -i 'https://YOUR-SERVICE.onrender.com/api/health'
curl -i 'https://YOUR-SERVICE.onrender.com/api/produce'
```

Expect `200` with `{"status":"ok"}` from health. Unless demonstration seeding is enabled, a new database returns `{"listings":[]}`. Use the README register/login examples with the Render base URL, then redeploy and confirm the account persists. Data lives in Turso, so Render restarts do not erase it. Seeding runs only on an empty users table; turning seeding off does not remove previously seeded accounts.

Render Free sleeps after 15 minutes without traffic, and the next request can take about a minute to wake it. Allow for this delay during demonstrations. Do not use keep-alive traffic to bypass free-tier behavior. Monitor Render and Turso usage to stay within the free allowances.

## Local verification

Run `npm test`, `npm run lint`, and `npm run build`. Without Turso variables and outside production, the same asynchronous client uses the local SQLite file at `server/data/agroconnect.db`; tests create isolated databases. To try a remote development database, set both Turso variables in the process environment. Use a separate database from production.

Build the API image with `docker build -t agroconnect-api .`. To run it in production mode, provide `JWT_SECRET`, `TURSO_DATABASE_URL`, and `TURSO_AUTH_TOKEN`, and map the API port. No volume mount is required. Local tests cannot verify your hosted credentials, network access, or provider quotas; verify the deployed endpoints after configuring the accounts.

No hosted accounts or resources are created by these files.
